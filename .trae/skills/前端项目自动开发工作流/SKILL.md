# 前端项目自动开发工作流

## 功能描述
作为面向 Claude Code 的前端开发 Skill，本工作流用于在**已有前端项目**中自动完成从需求理解到代码交付的完整链路，不负责新建项目骨架。

核心能力：
- 自动嗅探项目技术栈，如 React、Vue、Vite、Next.js、Tailwind、Ant Design、Element Plus。
- 自动分析目录结构、公共组件、路由、状态管理、接口封装和样式体系。
- 根据用户需求精准定位修改点，尽量复用现有组件和工具函数。
- 在修改后自动做基础自检，如类型、语法、构建、Lint、运行说明整理。
- 保持改动边界清晰，不随意重构与需求无关的代码。

## 何时调用
当用户出现以下意图时应立即调用本 Skill：
- 让我开发某个前端需求。
- 修改某个前端页面或组件。
- 修复前端页面、交互、样式、接口联调问题。
- 根据截图、原型、Figma、蓝湖还原前端页面。
- 在现有前端项目里新增模块、表单、弹窗、列表、详情页。
- 需要 Claude Code 在前端项目中自主完成一轮开发工作。

## 不适用场景
以下场景不要使用本 Skill，或需要切换更合适的 Skill：
- 从零创建全新项目脚手架。
- 单纯生成 Git 分支名、发布 Tag、处理飞书 Bug。
- 用户明确要做后端服务、数据库设计、运维部署。

## 自动执行流程

### 1. 需求理解
- 先提炼用户目标、交付物、影响页面、目标行为和边界约束。
- 若信息足够明确，直接进入分析和开发。
- 若存在关键歧义且会影响实现方向，再向用户提出最少量问题。

### 2. 项目规范嗅探
进入项目后优先检查以下内容：
- `package.json`、锁文件、构建脚本、Lint 脚本、测试脚本。
- `src` 目录结构、路由定义、布局层、页面层、组件层。
- 公共组件、请求封装、状态管理、常量、主题变量、国际化方案。
- 样式方案，如 CSS Modules、SCSS、Less、Tailwind、Styled Components。
- 命名风格、文件组织方式、已有注释习惯、错误处理方式。

如果项目已有组件和工具函数，优先复用；除非用户明确要求，否则不要引入新的重型库。

### 3. 开发策略
在实现过程中遵守以下规则：
- 只修改与当前需求直接相关的文件。
- 优先做局部增量修改，避免无关重构。
- 尽量沿用现有类型定义、接口封装和组件抽象。
- 若需新增文件，命名和目录层级必须符合现有项目习惯。
- 新增函数时添加函数级注释，注释要简洁、说明作用即可。
- 如果存在多个可行方案，优先选择侵入性小、可维护性高的方案。

### 4. 自主开发节奏
默认采用“能自动完成就不中断”的策略：
- 搜索相关代码。
- 阅读关键文件。
- 制定最小修改方案。
- 直接完成实现。
- 完成后自检并汇总结果。

仅在以下情况才中途询问用户：
- 需求存在互斥实现路径。
- 缺失关键业务规则。
- 需要用户提供接口字段、设计稿细节或测试账号。
- 发现现有代码存在高风险异常，继续修改可能造成副作用。

### 5. 修改后自检
完成代码后，按项目实际能力尽量执行：
- 类型检查。
- Lint。
- 单测或相关局部测试。
- 构建或开发环境运行验证。
- 检查新增依赖是否必要。
- 检查 import、变量、样式作用域、空值分支、异常提示是否合理。

如果无法执行某项校验，需要明确说明原因和替代验证方式。

### 6. 交付输出
交付时应包含：
- 改了什么。
- 主要涉及哪些文件。
- 已做了哪些校验。
- 还需要用户补充或手动验证什么。
- 如果适合，给出运行命令、测试步骤或后续发布建议。

## 工作边界
- 不要未经允许创建新的前端项目脚手架。
- 不要为了“看起来更规范”而大范围移动文件或重构目录。
- 不要擅自替换用户现有技术栈。
- 不要修改与当前需求无关的环境配置。
- 不要忽略编译、Lint 或运行报错。

## 推荐触发语句示例
- 用这个 Skill 帮我改前端页面。
- 在当前 React 项目里直接完成这个需求。
- 帮我在现有 Vue 项目中自动开发这个模块。
- 按截图把这个前端页面做出来。
- 帮我修复这个前端交互 Bug。

## 成功标准
满足以下条件时，视为一次合格执行：
- 正确识别项目技术栈和约束。
- 修改范围聚焦且不破坏原有结构。
- 代码实现符合现有项目风格。
- 已完成必要自检并向用户清晰交付。
