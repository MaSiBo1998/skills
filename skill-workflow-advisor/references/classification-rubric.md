# 分类准确性检查表

用于审查 `front-workflow` 或任一子 skill 的触发、归类和调度是否准确。

## 归类层级

| 层级 | 判断问题 | 常见错误 |
| --- | --- | --- |
| 方向 | 这是 frontend、backend、flutter、workflow/meta 还是未知方向？ | 看到接口、设计图、发布词就直接进子场景，没有先判方向 |
| 主场景 | 用户真正要完成的业务目标是什么？ | 把辅助材料当主目标，例如设计图抢占后台功能 |
| supporting capability | 哪些能力只是补输入、风险或验收？ | 因为出现关键词就机械串所有可选 skill |
| 沉淀收口 | 本次是否形成可复用判断标准？ | 明确重复问题没有沉淀，或把一次性事实写成通用规则 |

## 证据要求

- 强证据：用户明确目标、目标文件或目录、接口/设计/配置材料、现有代码结构一致。
- 中证据：用户目标明确但材料不完整，可写入 assumptions 后继续。
- 弱证据：只有单个关键词、零散文件名、单条文案，只能形成候选，不能直接定主场景。
- 阻塞证据：缺项目路径、目标模块、业务结论、关键外部依赖或高风险资金/风控/发布结论。

## 分类审查问题

1. 当前判定的 `primary_direction` 是否比 `primary_scene` 更早确定？
2. `primary_scene` 是否回答了用户真正要完成的目标？
3. 设计图、接口、告警、vendor、发布是否被正确降级为 supporting capability？
4. 可选 skill 是否有加入条件和跳过理由？
5. 信息不足时是否先做最小探索，而不是泛问完整需求？
6. 高风险场景是否只问必要业务结论？
7. 未知/复合需求是否进入 K 兜底并回落到最近可执行场景？
8. 分类错误是否已经补进回归样例？
9. 可复用修正规则是否交给 `workflow-self-improvement` 沉淀？
10. 源目录与 `.agents/.codex/.trae/.claude` 运行时目录是否同步？

## 输出建议粒度

- `P0`：会导致任务进入错误 skill、阻塞执行、跳过高风险确认或运行时加载旧规则。
- `P1`：会导致可选 skill 机械串联、回归漏测、沉淀漏触发或主/子 skill 重复维护。
- `P2`：文案不清、触发词缺少同义词、建议位置不够明确，但不影响当前任务完成。

## 回归补样原则

新增回归样例优先覆盖稳定判断标准，而不是单个项目事实。样例至少说明用户输入、期望主归属、辅助能力、沉淀判断和验证点。
