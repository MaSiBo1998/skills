# 设计图图片复原设计

本 skill 负责根据项目 `design/` 文件夹中的设计图图片复原前端页面。执行时必须尊重项目现有技术栈、组件风格和路由结构，不新建独立 demo 页面代替真实业务实现。

优先使用 `design-image-analysis` 输出的 375px 宽基准解析清单；没有解析清单时，先按 `design-image-analysis` 的规则完成读图分析，再进入实现。

## 输入与定位

1. 确认项目根目录。
2. 用户本轮直接提供可读取的截图时优先使用该截图；只有用户未提供图片时，才读取项目根目录 `design/` 文件夹并收集 `.png`、`.jpg`、`.jpeg`、`.webp`、`.gif` 图片。
3. 用户未提供截图且 `design/` 不存在或没有设计图时，先阻断并提示用户补充设计图；不要凭空设计。
4. 若有多张设计图，按文件名、尺寸、页面内容判断页面顺序和状态；无法判断时询问用户。单张截图且目标组件明确时，不扩展为多页面分析。
5. 内嵌 H5 / App WebView 设计图统一以 `375px` 作为逻辑设计宽度；用户提供的内嵌 H5 设计图默认就是 375 宽基准。若图片文件物理像素宽度是 `750px`、`1125px` 等，优先按 `@2x`、`@3x` 导出图理解，先换算回 375 逻辑宽，禁止把物理像素宽误判成新的设计基准。只有用户明确说明设计图不是 375 逻辑宽，或设计稿中存在可验证的非 375 画板标注时，才按 `scale = 375 / 原图宽度` 做额外换算，并说明依据。H5 还原时样式源码默认保留设计稿 `px`，通过入口 `setRem` + 构建阶段 postcss-px-to-rem 或项目既有等价方案输出 `rem`；不要把解析尺寸直接手写成 `rem`。运行时动态注入的尺寸或 CSS 变量若不会经过构建转换，必须使用同一基准工具从设计稿 `px` 转成 `rem`。
6. 打开设计图进行视觉分析，提取布局、间距、字体层级、颜色、按钮状态、图片资源、列表密度和移动端安全区。

## 切图资源

只有本次新增或替换切图时，才从项目资源目录中寻找可复用切图：

1. 优先递归检查 `src/assets`，并按项目实际结构补充检查 `src/assets/images`、`src/assets/img`、`assets`、`public` 下的图片、图标和背景资源。
2. 对比设计图中的 logo、图标、插画、背景、空状态、按钮图形等元素。
3. 能复用现有切图时，直接引用现有资源，不重复生成或复制。
4. 找不到必要切图时，先说明缺失资源；只有用户提供或项目已有提取方式时，才新增资源。
5. 不把 `design/` 中的完整设计图当成页面背景来糊弄复原，除非用户明确要求做静态预览。

## 切图命名规范

使用或新增切图前，必须规范化资源名称：

- 使用小写 kebab-case。
- 名称包含业务语义，避免 `image1`、`icon-final`、`tmp`、`copy` 这类无意义名称。
- 图标使用 `icon-场景-含义.ext`，例如 `icon-home-loan.png`。
- 背景使用 `bg-场景-含义.ext`，例如 `bg-login-header.webp`。
- 插画使用 `illus-场景-含义.ext`，例如 `illus-empty-order.png`。
- logo 使用 `logo-品牌-变体.ext`，例如 `logo-prestaone-light.png`。
- 重命名资源后，必须同步更新所有引用。
- 不批量重命名无关资源，只规范本次使用到的切图。

## 实现流程

1. 识别技术栈：
   - 读取 `package.json`、路由、页面目录、组件目录、样式方案。
   - 沿用项目既有框架、组件和 CSS 写法。
2. 建立设计映射：
   - 将每张设计图对应到目标页面、路由或组件。
   - 标注需要复原的结构、资源、状态和交互。
   - 用户直接提供单张截图且目标组件或状态分支明确时，复用 `design-image-analysis` 的差异清单，只读取目标实现和直接相关样式；清单与目标代码足以确定结果后立即进入开发，不继续扫描完整页面、资产目录或参考项目。
3. 开发页面：
   - 优先改真实业务页面，不额外做无入口页面。
   - 使用项目已有组件、变量、mixin、主题 token。
   - 设计图缺少某个现有业务模块不等于要删除该模块；还原页面时必须先检查当前代码中已有的 banner、轮播、埋点、轮询、原生 bridge、按钮回调、刷新和兜底展示等业务行为，默认保留，只调整目标视觉结构和样式。只有用户明确要求删除已有业务行为时才移除。
   - 同一组件存在多个状态分支时，按用户点名的状态分支逐一改造；不要把某个分支的视觉改造扩散到其他分支，也不要因为复用 CSS 而改变其他分支的既有渲染、跳转或 banner 展示。
   - 保持移动端布局稳定，避免文本、按钮、图片在窄屏溢出。
   - 图片元素设置明确尺寸、比例或容器约束，避免加载后布局跳动。
   - 同一功能的后续局部反馈只复核当前 diff、最新截图和目标文件后直接调整；除非反馈改变业务分支、原生桥、接口或公共组件范围，否则不重新执行完整设计分析。
4. 处理 `.gitignore`：
   - 只有本轮读取或新增项目根目录 `design/` 文件夹时，才检查目标项目根目录 `.gitignore`。
   - 使用项目 `design/` 且尚未忽略时，添加独立规则 `design/`；只使用用户本轮提供的外部截图时跳过该步骤。
   - 不删除已有规则。
5. 验证：
   - 单组件、局部样式、文案或单张图片替换默认走小需求快速验收：不启动 dev server、不控制浏览器、不截图、不执行生产构建。
   - 快速验收只检查设计图 375px 基准解析结果与目标分支的结构/样式 diff、目标资源引用是否存在且只影响预期组件，以及本次新增 CSS、图片格式和尺寸约束是否引入局部兼容风险。
   - 涉及少量 TSX/JSX 或资源 import 时，按 `h5-testing-checklist` 使用 `focused`，复用已有类型检查结果或只执行一次最小静态/类型检查；通过后停止，不再追加构建或运行态验证。
   - 只有跨页面或公共组件重构、共享主题语义变化、接口或主流程、路由、构建配置、rem/viewport 入口、发布任务，或用户明确要求时才执行生产构建。
   - 浏览器和截图只在用户明确要求，或大型布局改造确实需要运行态证据时使用；单个现有页面内的 Popup、Modal、Dialog 或局部 overlay，即使接近全屏或附带参考截图，也不视为大型布局改造。
   - 不得仅为验证单个弹窗或局部截图还原而创建 mock API、临时 demo/测试页、Playwright fixture 或截图脚本；确有只能运行态确认的阻塞风险时，先说明具体风险点和所需证据，再按 `h5-testing-checklist` 升级。
   - 无法自动验证的真实 App WebView 行为列为人工验收项。

## 交付要求

交付时说明：

- 使用了哪些 `design/` 设计图。
- 是否使用了 `design-image-analysis` 的 375px 基准解析清单。
- 复原了哪些页面、路由或组件。
- 复用了哪些资源目录中的切图。
- 重命名了哪些切图以及引用更新位置。
- `.gitignore` 是否已加入 `design/`。
- 执行了哪些最小静态、类型、构建或视觉验证；小需求跳过构建和视觉验证时，说明按快速验收规则跳过。
- 仍需人工确认的设计差异。
