# Frontend Dev Workflow

一个面向 Claude Code 的前端开发工作流 Skill。

它不是脚手架生成器，而是一个可执行的开发协议：当 Claude Code 进入**已有前端项目**时，这个 Skill 负责驱动整条开发链路，从需求理解到代码修改，再到自检和交付说明。

---

## 什么时候必须触发

当用户出现以下意图时，应优先触发本 Skill：
- 开发一个前端需求
- 修改页面、组件、弹窗、表单、列表、详情页
- 修复前端 Bug、交互问题、样式问题、状态问题
- 接入或调整接口
- 根据截图、原型、Figma、蓝湖还原页面
- 让 Claude Code 在当前 React / Vue 项目里自动完成一轮开发

即使用户表达比较口语化，也应识别为触发信号，例如：
- “帮我把这个页面做了”
- “在这个项目里直接改掉”
- “你自己看代码帮我实现一下”
- “按设计稿还原一下页面”
- “这个前端问题帮我修掉并自检”

---

## 什么时候不要触发

以下场景不应使用本 Skill：
- 从零创建新前端脚手架
- 纯 Git / Tag / 发布流操作
- 后端接口实现、数据库设计、运维部署
- 纯文档整理、文案润色、非代码任务

## 工作协议

### Step 1. 需求理解
先提炼以下信息：
- 用户想要什么结果
- 影响哪些页面、组件、交互、接口
- 有哪些显式边界和隐式风险
- 用户有没有指定技术约束、视觉约束或交付约束

若信息足够明确，直接进入下一步；若存在关键歧义，先提最少量问题。

### Step 2. 技术栈与规范嗅探
进入项目后，优先检查：
- `package.json`、锁文件、构建命令、Lint 命令、测试命令
- 页面目录、组件目录、路由目录、状态目录、接口目录
- 样式体系，如 CSS Modules、SCSS、Less、Tailwind、Styled Components
- UI 组件库，如 Ant Design、MUI、Element Plus、Naive UI
- 请求封装、类型定义、国际化、权限控制、主题方案

目标是先回答三个问题：
1. 这个项目怎么组织代码
2. 这个项目偏好怎么写代码
3. 这次需求最可能改哪些文件

### Step 3. 精准定位
使用搜索和阅读快速定位：
- 相关页面
- 相关组件
- 相关 hooks / composables
- 相关路由
- 相关接口封装
- 相关样式文件

只读关键文件，不盲目通读整个项目。

### Step 4. 最小实现方案
形成“最小但完整”的修改方案：
- 优先复用已有组件、工具函数和类型
- 只改与当前需求直接相关的代码
- 避免无关重构
- 非必要不增加新依赖
- 新增文件时遵循项目现有命名和目录习惯

### Step 5. 自动开发
默认采用“能自动完成就不中断”的执行策略：
1. 修改代码
2. 补齐必要的类型和样式
3. 若需要，新增少量辅助文件
4. 保持逻辑闭环

新增函数时添加函数级注释，注释要简洁说明作用。

### Step 6. 自检
根据项目能力尽量执行：
- 类型检查
- Lint
- 构建
- 局部运行验证
- import、变量、空值分支、样式越界检查

如果某项无法执行，必须在交付时说明原因。

### Step 7. 交付说明
完成后输出应包含：
- 做了什么修改
- 涉及哪些关键文件
- 做了哪些校验
- 哪些地方建议用户手动验证
- 如有必要，给出运行命令或后续建议

---

## 强约束

- 不要为了“顺手优化”而大范围重构
- 不要擅自切换技术栈
- 不要无理由新增重型依赖
- 不要在未确认风险前改动全局配置
- 不要忽略构建、Lint 或运行报错

---

## 成功标准

满足以下条件，视为一次合格执行：
- 正确识别项目技术栈与代码风格
- 改动范围小而准确
- 尽量复用原有代码体系
- 完成必要自检
- 交付说明清晰，可直接给用户确认
