# H5 Embedded App Workflow

这是一个面向 Claude Code 的专项开发工作流 Skill。

它用于处理这样一类项目：已经存在一个可运行的 **H5 内嵌 app 基准项目**，后续所有需求都基于这个项目持续二开。新需求的页面结构、接口域名、参数名、设计稿会变化，但底层业务模式、接口返回结构和取值语义保持一致。

这个 Skill 的目标，是让 Claude Code 在这类项目里稳定执行一条固定工作流：
- 以现有 H5 项目为基准进行开发
- 接入新的 YApi 接口文档
- 基于接口文档自动识别接口返回结构不变、参数名变化的对应关系
- 根据 Figma 设计图一比一还原页面
- 完成基础开发后进行模拟测试与验收整理

---

## 什么时候必须触发

当用户出现以下意图时，应优先调用本 Skill：
- 基于现有 H5 内嵌项目继续开发新需求
- 在现成 H5 项目上改页面、改逻辑、改接口
- 接入新的 YApi 文档到旧项目
- 接口请求地址变了，参数名变了，但结构语义基本一致
- 需要根据 Figma 设计稿进行像素级还原
- 需要 Claude Code 自动完成开发并模拟测试验收
- 用户已提供 YApi 链接和 Figma 文档，希望后续连续完成所有开发任务

即使用户说得比较口语化，也应触发，例如：
- “就在这个 H5 项目上继续改”
- “这次换一套接口文档，但结构差不多”
- “按新的 Figma 改成一模一样”
- “你直接在基准项目上做完，并自测一下”

---

## 不适用场景

以下场景不要使用本 Skill：
- 从零新建 H5 项目脚手架
- 纯后端开发、数据库设计、运维部署
- 与现有基准项目完全无关的全新产品开发
- 单纯生成 Git 分支名、发布 Tag、处理飞书 Bug

## 核心工作流

### Step 1. 基准项目识别
进入项目后，先确认：
- 当前是否为已有 H5 内嵌 app 项目
- 项目技术栈、目录结构、构建命令、路由结构
- 公共组件、公共布局、请求封装、工具函数、状态管理
- 当前项目中哪些页面或模块最接近新需求

目标不是重建，而是找到“这次需求应该基于什么旧实现改”。

### Step 2. 旧逻辑与新需求对齐
优先梳理：
- 旧页面的交互路径
- 旧接口的请求参数与返回结构
- 新需求中哪些能力可直接复用
- 哪些地方只需要改接口地址
- 哪些地方只是参数名变化
- 哪些地方需要新增字段映射层

如果返回结构和语义不变，但参数名变化，应优先根据接口文档做“文档驱动的字段适配”，而不是把所有旧逻辑全部推倒重写。

### Step 3. YApi 文档接入分析
当用户提供 YApi 文档后，执行以下动作：
- 读取接口路径、请求方法、域名或 baseURL 变化
- 提取新的请求参数名
- 对照基准项目已有接口封装，基于接口文档自动识别字段对应关系
- 确认返回值结构、状态码约定、错误提示规则是否沿用旧模式
- 若存在旧字段与新字段一一对应关系，优先沉淀在接口层或数据适配层，而不是手工维护额外模板

重点关注：
- 请求地址变化
- 参数名变化
- 返回结构是否一致
- 业务取值语义是否一致
- 页面展示字段是否仍可沿用旧逻辑

### Step 3.5. 自动连续执行规则
当用户已经提供以下两类信息后，应默认进入连续执行模式：
- YApi 链接或等效接口文档
- Figma 链接、设计图或等效设计文档

进入连续执行模式后：
- 默认视为开发上下文已基本齐备
- Claude Code 应连续完成分析、开发、自检和模拟测试
- 除非出现阻塞性问题，否则不要在中途反复询问用户确认

仅在以下情况允许中途提问：
- 链接失效、无法读取或权限不足
- 接口文档与页面需求存在明显冲突
- Figma 设计信息缺失到无法还原关键页面
- 项目现有代码异常，继续修改风险过高
- 缺少测试账号、环境变量或真实联调条件，导致无法继续验证

### Step 4. Figma 一比一还原
当用户提供 Figma 设计图时，执行以下动作：
- 优先读取页面布局、色值、间距、字号、圆角、图标、状态样式
- 搜索项目中可复用的布局组件、表单组件、按钮、卡片、弹窗
- 能复用就复用，不能复用时再做最小新增
- 还原时优先保证视觉一致、层级一致、交互一致
- 如果项目已有设计 token、样式变量、主题体系，优先沿用

目标是“基于现有项目体系做高还原”，不是为了还原而重做整个 UI 系统。

### Step 5. 精准开发
开发时遵守以下规则：
- 只修改与本次需求直接相关的页面、组件、接口封装、样式文件
- 优先复用旧页面和旧逻辑
- 新增函数时添加函数级注释
- 非必要不引入新依赖
- 不进行无关重构
- 如需做参数兼容，优先放在接口层或数据适配层，而不是在页面里到处散落转换逻辑

### Step 6. 模拟测试与验收
完成代码后，必须进行一轮“模拟测试验收”：
- 检查页面渲染是否符合设计稿
- 检查主要交互流程是否闭环
- 检查接口请求是否已指向新地址
- 检查请求参数是否已完成新旧字段映射
- 检查返回值解析、空态、异常态、加载态
- 检查按钮状态、表单校验、弹窗反馈、跳转逻辑
- 如项目支持，执行类型检查、Lint、构建或局部运行验证

如果不能真实联调，应明确标注为“模拟测试”，并说明模拟依据。

### Step 7. 验收交付说明
交付时输出必须包含：
- 本次基于哪个旧模块或旧页面进行二开
- 新的 YApi 接口改了哪些地址和参数
- 哪些字段做了映射适配
- Figma 还原涉及哪些关键样式或组件
- 已完成哪些模拟测试
- 还需要用户做哪些真实验收或联调验证

---

## 强约束

- 不要把已有基准项目当成新项目重做
- 不要忽略“结构相同、字段名变化”这个核心前提
- 不要脱离接口文档手工猜测字段映射关系
- 不要在页面层到处写散乱的字段转换
- 不要为追求视觉还原而推翻整个原有组件体系
- 在 YApi 和 Figma 已提供后，不要无必要地反复询问用户确认
- 不要跳过测试说明和验收清单

---

## 推荐触发语句

- 用 H5 内嵌项目二开工作流帮我做这个需求
- 基于当前 H5 项目接入新的 YApi 文档并完成页面修改
- 这个接口结构一样，但参数名变了，你按旧项目改好
- 按新的 Figma 设计稿把这个 H5 页面做成一模一样
- 在现有 H5 基准项目上完成开发并模拟测试验收

---

## 成功标准

一次合格执行应满足：
- 正确识别当前基准项目及可复用模块
- 正确完成新旧接口地址与参数映射
- 尽量复用旧逻辑和旧组件，而不是重写
- 页面视觉和交互尽量贴近 Figma 设计稿
- 输出一份清晰的模拟测试和验收说明
