# 02 API Doc And Mapping

## 核心假设

这个工作流最关键的前提是：

- 接口返回结构相同或高度相似
- 业务语义和取值逻辑相同
- 变化主要在请求地址、参数名、局部字段名

## 推荐策略

这里的前提是：**字段对应关系以接口文档为准来识别**，不是额外再维护一份独立的人工模板。

## 推荐输入优先级

为了让自动解析更稳定，建议优先使用以下文档顺序：

1. `swaggerApi.json`
2. `api.json`
3. `api.md`
4. `api.html`

优先原则：
- 优先结构化 JSON
- 次选平台原始 JSON
- Markdown 作为人工辅助
- HTML 只作为最后兜底参考

### 1. 先从接口文档识别对应关系
优先整理：
- 旧请求参数 -> 新请求参数
- 旧字段名 -> 新字段名
- 旧接口地址 -> 新接口地址

### 2. 映射层位置
优先放在：
- 接口封装层
- 请求参数构造层
- 数据适配层

避免把转换逻辑散落在多个页面组件中，也不要脱离接口文档手工猜测字段。

### 3. 页面层原则
页面层尽量继续使用旧语义字段，除非确实需要整体重构。

## 验证重点

- 请求是否命中新接口
- 参数名是否映射正确
- 返回值解析是否仍然适配旧页面逻辑
- 错误提示和空态逻辑是否仍然成立
