# 02 API Doc And Mapping

## 核心假设

这个工作流最关键的前提是：

- 接口返回结构相同或高度相似
- 业务语义和取值逻辑相同
- 变化主要在请求地址、参数名、局部字段名

## 推荐策略

**字段对应关系以接口文档为准来识别**，不是额外再维护一份独立的人工模板。

## 推荐输入优先级

为了让自动解析更稳定，建议优先使用以下文档顺序：

1. `swaggerApi.json` — **最推荐**，结构最标准，适合作为工作流主输入
2. `api.json` — 适合补充 YApi 原始字段信息
3. `api.md` — 适合人工查阅
4. `api.html` — 更偏展示，不适合作为主解析来源

优先原则：
- 优先结构化 JSON
- 次选平台原始 JSON
- Markdown 作为人工辅助
- HTML 只作为最后兜底参考

## 自动化解析流程（SKILL.md Step 2.5）

当 Claude Code 读取 JSON 接口文档时的动作：

### 1. 读取与提取
- 从 `swaggerApi.json` 提取 paths、methods、parameters、responses
- 从 `api.json` 提取字段列表

### 2. 新旧对照
- 逐接口对比基准项目和接口文档
- 路径变化：`旧 /api/v1/xxx` → `新 /api/v2/xxx`
- 参数名变化：`旧 userId` → `新 user_id`
- 返回结构变化：是否一致 / 增加字段 / 减少字段

### 3. 输出映射表
结构化映射表格式：
- 旧路径 → 新路径
- 旧参数 → 新参数
- 旧字段 → 新字段
- 映射状态：自动 / 需确认

### 4. 代码适配
- 基于映射表自动修改接口层代码或生成适配层
- 映射层位置优先放在接口封装层或数据适配层
- 页面层尽量继续使用旧语义字段

### 5. 人工确认项
- 无法自动映射的字段标记为"需人工确认"
- 结构变更较大的接口额外标注

## 验证重点

- 请求是否命中新接口
- 参数名是否映射正确
- 返回值解析是否仍然适配旧页面逻辑
- 错误提示和空态逻辑是否仍然成立
